The legacy package is primarily dashboard and analysis code. It does not contain
the original raw EIA ingestion path for the current dated versions; those
versions read already-cleaned database tables, cache parquet locally, and publish
HTML/PDF artifacts. The production source of truth in this repo should be raw
EIA Open Data API rows upserted into `eia` tables.

Legacy dashboard fields included date spine columns, respondent identity columns
such as `is_iso`, `time_zone`, `respondent`, `region`, and
`balancing_authority_name`, and derived daily fields such as `total_mw`,
`renewables_mw`, `thermal_mw`, `wind_mw`, `solar_mw`, `natural_gas_mw`,
`coal_mw`, `oil_mw`, `nuclear_mw`, `hydro_mw`, `battery_mw`, and
`natural_gas_pct_of_thermal`. The weather-adjusted version renamed those fields
for presentation, including `Load`, `Net Load`, `Gas`, `Coal`,
`Gas % of Thermal`, and `Coal % of Thermal`.

Migration stance:

- Do not recreate the legacy `eia_cleaned.eia_930_daily` table as the raw
  ingestion contract.
- Promote raw EIA Open Data API v2 daily endpoints first, then rebuild curated
  dashboard shapes from those raw tables.
- Treat weather-adjusted regressions and Tableau PDF capture as derived
  presentation logic, not source scrapes.

## Promoted Raw Sources

| Source | Endpoint | Destination | Grain | Key | Status |
| --- | --- | --- | --- | --- | --- |
| Daily generation by fuel type | `/electricity/rto/daily-fuel-type-data` | `eia.eia_930_daily_generation_by_fuel` | `period x respondent x fueltype x timezone` | `period, respondent, fueltype, timezone` | Tracked and promoted in `backend.scrapes.eia.eia_930_daily_generation_by_fuel`. |
| Daily region data | `/electricity/rto/daily-region-data` | `eia.eia_930_daily_region_data` | `period x respondent x type x timezone` | `period, respondent, type, timezone` | Implemented locally, but the runtime, DDL, tests, and systemd files are currently untracked in this checkout. |

Both EIA-930 daily endpoints return multiple timezone variants for the same
period/respondent combination. The raw tables preserve `timezone` in the
primary key. Downstream code selects a preferred timezone per dashboard region.

Source values are daily `megawatthours`. Dashboard/API presentation converts
them to daily average MW by dividing by `24`.

Daily region `type` values currently targeted by the local implementation:

- `D`: demand
- `DF`: day-ahead demand forecast
- `NG`: net generation
- `TI`: total interchange

## Backfill And Rerun

DDL is operator reference SQL and must be applied with `helios_admin` before
writes are enabled. Apply table files first, then index files separately with
autocommit enabled because the index scripts use `CREATE INDEX CONCURRENTLY`.

Default module runs:

```powershell
python -m backend.orchestration.eia.eia_930_daily_generation_by_fuel
python -m backend.backfills.eia.eia_930_daily_generation_by_fuel
python -m backend.orchestration.eia.eia_930_daily_region_data
python -m backend.backfills.eia.eia_930_daily_region_data
```

Backfill wrappers are idempotent and call the same raw upsert path with
`run_mode=backfill` metadata in `ops.api_fetch_log`. The current defaults are a
31-day replay, 31-day chunks, 4-second inter-chunk delay, and 366-day maximum
window unless the function arguments are changed by an operator.

## Current Frontend Consumer

The local DEV EIA dashboard reads:

- `eia.eia_930_daily_generation_by_fuel` for daily fuel mix.
- `eia.eia_930_daily_region_data` for demand.
- `weather.wsi_daily_weighted_degree_day_observations` for WSI electric CDD/HDD
  weather response.

Frontend files:

- `frontend/lib/eiaGeneration.ts`
- `frontend/app/api/eia-generation/route.ts`
- `frontend/components/eia/EiaGenerationDashboard.tsx`

The route presents one row per `period x respondent` after preferred-timezone
selection. It aggregates fuel types into gas, coal, nuclear, hydro, wind, solar,
and other buckets, computes total generation as the sum of fuel rows, computes
thermal as gas plus coal, and derives percentage shares from daily average MW.
Solar and wind use the core EIA `SUN` and `WND` fuel codes; integrated-battery
and storage categories such as `SNB`, `WNB`, `BAT`, `PS`, and `UES` roll into
Other unless a future dashboard adds explicit storage columns.
Weather response is a dashboard calculation over EIA-930 demand rows and WSI
weather buckets, not an EIA source scrape.

## Remaining Migration Work

- Commit and deploy the daily region-data raw scrape files if they are intended
  to be production-bound.
- Verify `eia.eia_930_daily_region_data` in production after deployment and
  backfill; the DEV dashboard depends on `D` rows for true demand.
- Build a curated EIA-930 daily mart only after both raw tables are stable. The
  mart should reproduce the old `eia_cleaned.eia_930_daily` semantics from raw
  rows, including preferred timezone selection, respondent labels, fuel pivots,
  `Load`, `Net Load`, `Thermal`, and gas/coal thermal percentages.
- Keep weather-adjusted demand/modeling as a downstream dashboard or modelling
  layer backed by `weather.wsi_daily_weighted_degree_day_observations`; do not
  fold WSI weather fields into the raw EIA scrape table.
- Do not add an hourly EIA-930 table unless a separate source contract and
  downstream use case require hourly EIA-930 data. The current dashboard target
  is covered by daily raw endpoints.
